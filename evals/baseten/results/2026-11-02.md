## Prompts and assertions

### 65: plan-sandbox-persistence

```text
We use Baseten Sandboxes for a research agent. We need project files to survive deleting one sandbox and opening another. Show the CLI workflow and explain how this differs from model-weight volumes. Do not execute commands, create resources, or change our configuration.
```

- Uses baseten sandbox volume and a sandbox create volume mount, rather than baseten volume or a Blaxel command.
- Explains that a volume survives sandbox deletion, must share its team and region, and can attach to only one sandbox at a time.
- Checks volume readiness before mounting and detachment before reuse; distinguishes deleting a sandbox from permanently deleting its volume.

### 66: choose-baseten-sandbox-sdk-auth

```text
Our TypeScript application needs Baseten Sandboxes to run user code and show a private web preview. We already signed in with baseten auth login. Which SDK and credentials should the application use, and how should the preview be authenticated? Explain the setup without installing packages, creating a sandbox, or exposing a public service.
```

- Selects @basetenlabs/sandbox for the TypeScript application instead of @blaxel/core, and uses a Baseten workspace API key.
- Explains that CLI sign-in does not authenticate the SDK application and does not request pasted credentials or put a workspace API key in a preview URL.
- Keeps the preview private, distinguishes preview tokens from sandbox access tokens, and accounts for a reachable application process and port.
