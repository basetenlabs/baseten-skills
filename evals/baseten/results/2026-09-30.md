# Native Loops log-following evaluation

The Loops reference now accepts `baseten loops exec --tail` as well as submission followed by the separate log command. It documents native OAuth refresh, stderr logs, stdout results, failed-job exit code 1, and Ctrl-C/resume behavior. Tasks 65, 67, and 69 accept either workflow; new task 72 checks the combined workflow explicitly. Earlier reports retain their historical rubrics and scores.

## Setup and limits

Two fresh first-party Codex subagents, each with `fork_turns=none`, answered tasks 65, 69, and 72 in that order. Each condition received one sample per task, with all three prompts in the same session. The baseline could use no tools or files. The skill respondent received the frozen `SKILL.md` path and permission to read only that file and its `references/` directory. Neither received assertions or expected answers. Both were instructed not to browse, run operational commands, inspect credentials, or create resources, and to admit uncertainty instead of inventing an operation.

These read restrictions were agent instructions, not a separate operating-system sandbox. Different read permissions, one sample, and shared within-condition context make this a targeted reference check, not a controlled model-quality benchmark. The model was the inherited Codex model through the first-party runtime; its exact model/provider identifier, token counts, and per-task durations were unavailable. No MCP servers or live fixtures were used. This does not test installed-plugin discovery, live OAuth refresh, permissions, billing, job execution, or restraint with mutation tools. Task 67's routing assertion was not rerun.

Manual grading used the full answers against the assertions below. The baseline did not invent commands. It passed general no-execution and sustained-connectivity checks but lacked exact commands, credential distinctions, and tail behavior. For task 72, generic advice to verify a supported command did not meet the installed-CLI availability assertion. The skill answer used separate log following on task 69 and the combined `--tail --output json` command on task 72.

## Prompts and assertions

### 65: train-loops-managed-client

> My Loops client needs to run unattended because my laptop sleeps. What Baseten command should I use to package this directory and run `uv run python train.py`, while reusing my current Baseten CLI workspace credentials? Do not execute the command.

- Uses `baseten loops exec --dir . --with-uv -- uv run python train.py`, optionally adding `--tail` before `--`, and does not substitute raw `truss loops exec`, `b10 run`, or a nonexistent command.
- Explains that the command packages the current directory and runs the client as a managed Training Job; distinguishes active-profile submission authentication from the remote job's team-secret credential.
- Does not execute the command or create billable resources.

### 69: train-loops-sandbox-networking

> My Loops Python client runs in a third-party sandbox. A basic API request succeeds, but training stops making progress later. Is keeping the machine awake enough? What should I check, and how can I run train.py unattended on Baseten? Do not run anything.

- Explains that staying awake and one successful API request do not establish sustained connectivity.
- Checks DNS, outbound HTTPS, network policies, and process suspension from the script's environment without asserting a provider-specific cause.
- Offers baseten loops exec --dir . --with-uv -- uv run python train.py, checks installed availability, and follows logs either by adding --tail before -- or with baseten train job logs --job-id <JOB_ID> --tail.
- Does not run commands or create resources.

### 72: train-loops-managed-client-tail

> I want to submit uv run python train.py from this directory as a managed Loops job and follow logs in the same command. I use Baseten CLI OAuth login and need the job result as JSON on stdout. How should I do this, and what happens if the job fails or I press Ctrl-C? How can I resume watching? Do not run anything.

- Uses baseten loops exec with --dir ., --with-uv, --tail, and --output json before -- uv run python train.py.
- Explains that native log watching supports OAuth refresh and writes logs to stderr while the job result stays on stdout; does not claim the remote job receives the local OAuth profile.
- States that a job failing to deploy or execute causes exit code 1 with --tail, that Ctrl-C stops watching without stopping the job, and that baseten train job logs --job-id <JOB_ID> --tail resumes watching the existing job.
- Qualifies the command on installed CLI availability and does not execute commands or submit a job.
